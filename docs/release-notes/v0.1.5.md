这一版主要解决「App 详情页只画 4 个必经点位、实际有 5 个」。没有新功能。

## 少画的那个点：报文键序错了

App 拿到的必到点是 5 条，详情页只画出 4 个。查了很久，一直按「数据不对」的方向找——`position` 该发什么、`id` 该从几起、`runAreaId` 发 -1 还是真实围栏 id、`geoFencesJson` 要不要带 `distance`/`id`/`name`。每一条都改过、都实跑验证过，每次都是「还是 4 个」。

真正的原因是**键序**。

把项目退回到 11 月 11 日那个 commit（`13f7fdf`）单独编出来，用同一个账号、同一个时间段跑一条，App 里 5 个点全出来了。两版报文逐字段比对，差异只剩三处，逐个改、逐个实跑：

```
id 从 1 起 + 键序字母序（flag 开头）  → App 显示 4 个
id 从 1 起 + 键序 lon 开头           → App 显示 5 个
```

`fivePointJson` 里每个点的键序改回 `lon / lat / isFixed / pointName / glon / glat / position / flag / id / isPass / state`。

原因是 App 不按 JSON 键名取值，而是**按字段位置**解析每个点。`serde_json` 开了 `preserve_order`，键序直接决定序列化字节，顺序一错，从第 8 个字段起全部错位，最后那条点就读不出来。所以数据看着每个字段都对，App 看到的却少一条。

字母序那版是照真机样本 `rrid 1328288734` 排的——那份样本没有 App 截图佐证，谁也没验证过它显示几个点。以实测为准。

顺带把必到点 `id` 从 81 起改回 1 起。这个值在同一批真机数据里有三个量级（81..85 / 400..404 / 1..5），本身不承载语义，按 11-11 那版原样保留。**需要说明的是：`id` 和键序是同时改的，没有单独归因**，我确认的只是「键序错会少画点」，没确认「`id` 必须从 1 起」。分开验证每跑一次要占用一个时间段、还要重启服务，账号容易触发风控锁，没做。

## 拐角补位之后又把间距顶回去了

本地体检报「第 130 点间距 50.1m，超过 50m」挡住提交，但采样本身就是按 50 米上限生成的。

原因是顺序：`clamp_sample_gaps` 跑在 `nudge_to_corners` **之前**，拐角补位会把已经压好的间距重新撑开，而后面没有再检查。现在补位之后再压一次，两次的统计合并进一条日志，最后再加一道残差告警。实测最大间距从 50.1 米降到 27.3 米。

## 提交前核对当前会话账号

调试期间为了对比报文，中途登录过别的账号，回来忘了切，连着几条记录落到别人账号下。本地没有删除接口，只能去 App 里手动删。

`/api/run` 加了 `expectUid`：调用方显式给了就核对当前会话 uid，对不上直接拒，两边的 uid 都写进错误信息。不传则行为不变。

（这个校验第一版加错了位置——加到了 `handle_batch`，而 `/api/run` 走的是 `handle_run`，等于没加，又跑串了一条。已经挪到正确入口并验证过能拒。）

## 采样点 type 按最新真机口径

真机（实测账号，rrid 1362483656）的 `allLocJson` 里**没有任何打卡标记**，104 个点全是 `{0: 101, 3: 1, 5: 1, 6: 1}`，5 个必经点完全靠 `fivePointJson` 渲染。早先要求撒 `type=2` 是照 10-02 那份老样本写的，那套口径服务端已经不用了。

撤掉 `type=2`，`type` 改按 `{0, 3, 5, 6}` 分布。连带删掉因此变死的代码：`point_json_full` 的 `checkpoint_idxs` 参数、`build_points` 的 `fixed` 参数、`reserved` 集合、重复下标告警，净删 49 行。

398 个测试通过，clippy 零警告。

实跑验证（实测账号）：`rrid 1367193291`，14 号 09:20，2166 米，`id` 1..5、键序 `lon` 开头、`position` 0/29/33/37/40，App 详情页**5 个点位全部画出**，其中 `isFixed=1` 那个显示为橙色（与真机一致）。

## 已知未解决

`isFixed=1` 对应的点被画成橙色，而 11-11 那条真机记录同样位置上 `isFixed=1` 却是绿色。两条报文的该字段、`isPass`、`state`、键序、`runAreaId`、`geoFencesJson` 形状完全一致——既然报文里没有能区分它们的东西，橙色就不是报文决定的。最可能跟跑步时段有关：11-11 那条是白天 11:36 正常计分跑，而测试记录都落在 `11016 不在有效跑步时间内` 的兜底分支。未验证。
